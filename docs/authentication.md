# Authentication

How each principal proves who it is, what its access token contains, and how credentials are stored. Permissions after authentication are in [Security](security.md). The credential tables and the hash helper (`src/auth/credentialHash.js`) exist; token issuance and verification are not implemented yet.

## Principals

| Principal | Identity | Signs in with | Created by |
| --- | --- | --- | --- |
| Staff (SLSEA reader) | A `users` row | `email` and `password` | [Operator command](#operator-command); no public registration |
| Device | A `solar_installations` row; one device per installation | `meterId` and `deviceSecret` | [Operator command](#operator-command) when the installation is registered |
| Provisioner | A `provisioners` row, separate from staff | `username` and `password` | [Operator command](#operator-command); no API creates or promotes provisioners |

Passwords are chosen by the person and must be 15 to 128 characters ([NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) section 3.1.1.2 requires at least 15 for single-factor passwords and recommends allowing at least 64; the upper limit bounds hashing cost). Device secrets are generated by the server: 32 random bytes, base64url-encoded, shown once when created and never stored in plain form. Rotating a device secret replaces the old one.

## Operator command

Credentials are created and changed with `npm run credentials` against `DATABASE_URL`. There is no HTTP endpoint for this.

| Command | Effect |
| --- | --- |
| `npm run credentials -- staff-password <email>` | Sets or changes an existing staff user's password |
| `npm run credentials -- provisioner-password <username>` | Creates a provisioner, or changes an existing provisioner's password |
| `npm run credentials -- device-secret <meter-id>` | Generates a device secret for the installation, replacing any previous one |

- Passwords are never accepted as arguments, so they stay out of shell history and process lists. In a terminal the command asks for the password twice without echoing it. Otherwise it reads the first line of standard input, for scripted use.
- A generated device secret is written once to standard output, only after its hash is stored; all other messages go to standard error. It cannot be shown again, so a lost secret is replaced by running the command again.
- Changing a password or secret gives the credential a new version, which revokes earlier tokens.
- The command prints no password, secret (other than the new device secret), or hash, and stores only the hash.
- Staff users themselves are not created by this command. Their `users` row, with role and scope, is inserted separately.

## Token request

`POST /issue-token` takes one of these bodies. `principalType` selects the credential; unknown fields return 400.

| principalType | Other fields |
| --- | --- |
| `staff` | `email`, `password` |
| `device` | `meterId`, `deviceSecret` |
| `provisioner` | `username`, `password` |

Email, meter ID, and username are matched ignoring case and surrounding spaces, as their unique indexes are. A wrong secret, an unknown identifier, and a principal with no stored credential all return the same 401 response. For an unknown identifier the server still verifies against a fixed dummy hash, so response time does not reveal which identifiers exist.

A successful response is 200 with `Cache-Control: no-store`:

```json
{ "accessToken": "<JWT>", "tokenType": "Bearer", "expiresIn": 3600 }
```

## JWT claims

Tokens are signed with HS256 using the `JWT_SECRET` environment variable (at least 32 random bytes). Verification accepts only HS256.

| Claim | Staff | Device | Provisioner |
| --- | --- | --- | --- |
| `iss` | `solar-generation-api` | same | same |
| `aud` | `solar-generation-api` | same | same |
| `sub` | User ID | Installation ID | Provisioner ID |
| `principalType` | `staff` | `device` | `provisioner` |
| `credentialVersion` | Current `credential_version` of the credential used | same | same |
| `iat` | Issue time | same | same |
| `exp` | `iat` + 1 hour | `iat` + 1 hour | `iat` + 15 minutes |

Tokens carry no role, jurisdiction, or permission list. On each request the server loads the principal named by `sub` and `principalType`: a staff user's role and province or district come from the `users` row, and a device may write only to the installation in `sub`. Scope changes therefore apply at once, and a deleted principal's token stops working.

A token is also rejected if its `credentialVersion` differs from the stored `credential_version`. The database gives a credential a new random version whenever its hash changes, so changing a password or rotating a device secret invalidates every earlier token, including one issued in the same second. A time comparison such as `iat < changed_at` cannot guarantee that, because `iat` has whole-second precision.

## Credential storage

Credentials are security data, not domain attributes, so they live in their own tables rather than on `users` or `solar_installations`.

| Table | Key | Stores |
| --- | --- | --- |
| `user_credentials` | `user_id`, one per user | `password_hash`, `credential_version`, `changed_at` |
| `device_credentials` | `installation_id`, one per installation | `secret_hash`, `credential_version`, `changed_at` |
| `provisioners` | `id`; `username` unique ignoring case and surrounding spaces | `username`, `password_hash`, `credential_version`, `changed_at` |

- Every secret is stored only as an scrypt hash in PHC string form: `$scrypt$ln=15,r=8,p=3$<salt>$<hash>`, with a 16-byte random salt and a 32-byte derived key, both base64 without padding. N = 2^15, r = 8, p = 3 is one of the [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt) minimum settings; it needs about 32 MB per hash, less than N = 2^17 with p = 1. scrypt is built into Node, so no native package is needed.
- The parameters are stored in each hash, so they can be raised later without invalidating existing hashes. Verification rejects a stored hash that would need more than 64 MiB (128 x N x r bytes), more work than N x r x p = 2^20, or a salt or key longer than 64 bytes, so a bad row cannot exhaust the server. This allows every OWASP setting up to N = 2^16, r = 8, p = 2.
- Secrets are Unicode-normalized (NFC) before hashing, so equivalent forms of the same characters verify alike.
- The database rejects any value that is not in this hash format, so a plaintext secret cannot be stored by mistake.
- `credential_version` (a random UUID) and `changed_at` are set by the database when a credential is created and whenever its hash changes; neither can be written directly. The version revokes tokens; `changed_at` is kept for auditing.
- Deleting a user or installation deletes its credential. An installation with readings cannot be deleted, so its device credential stays with it.
- Secrets and hashes never appear in API responses or logs.

Token requests should be rate-limited per client and identifier. That limit is designed with the token endpoint.
